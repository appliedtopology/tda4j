> **Status: a proof of concept.** This is a library-only experiment: there is no command-line or MATLAB entry point for it, it is
> only practical for small groups and low degrees (see [the cost](#the-cost)), and it is here because it shows an unusual use of the
> machinery rather than because it is the best way to compute group cohomology. Real group-cohomology software uses far smaller
> constructions.

Every finite group `G` has a **classifying space** `BG`, a space whose topology records the group's algebra: the homology of `BG` is
the *homology of the group*, a central invariant in algebra. A chain of subgroups `H_0 ≤ H_1 ≤ ... ≤ G` gives a chain of classifying
spaces `BH_0 ⊂ BH_1 ⊂ ... ⊂ BG`, which is exactly the shape of input persistent homology wants. The result is a barcode that follows
group homology as the group *grows*: which classes appear when you pass to a bigger subgroup, which are identified with each other,
and which survive all the way up to `G`.

This tutorial computes the homology of the symmetric group on three letters, then the persistent homology of a chain of subgroups
of the symmetric group on four.

## The classifying space and its homology

`BG` is built from the group itself, with no choices: one vertex, one edge for each non-identity element, one triangle for each
pair of non-identity elements (recording their product), and so on in every dimension, with `(|G| - 1)^n` cells in dimension `n`.
It is infinite, but the homology up to a given degree needs only finitely many cells.

```scala sc:nocompile
import scala.language.experimental.modularity
import org.appliedtopology.tda4j.TDAlab

val lab = TDAlab(2)
import lab.{*, given}

val s3 = groups.FiniteGroup.symmetric(3)
val s3Homology = Seq(2, 3).map(p => p -> groups.ClassifyingSpace.bettiNumbers(s3, 4, p)).toMap
// 2 -> Vector(1, 1, 1, 1, 1)     3 -> Vector(1, 0, 0, 1, 1)
```

`bettiNumbers(group, maxDegree, p)` gives the dimensions of `H_n(G; F_p)` for `n` up to `maxDegree`, with coefficients in the field with
`p` elements. The answers carry group theory that you can check by hand:

* Over `p = 2` the answer is one class in every degree, `1, 1, 1, 1, 1`, exactly that of the cyclic group of order 2. That is not an accident: the
  symmetric group on three letters has a subgroup of order 2 whose index, 3, is odd, and an odd index is invisible over the field
  with 2 elements.
* Over `p = 3` the pattern is `1, 0, 0, 1, 1`: classes in degrees 3 and 4 (and, continuing, 7, 8, ...), which is what the cyclic subgroup of order 3 would
  contribute once you account for how the element of order 2 acts on it.

## A chain of subgroups

Now the persistent version. Take the symmetric group on four letters, 24 permutations, and a chain of four subgroups of it: the
group `⟨(01)⟩` generated by swapping the first two letters (order 2); `⟨(01), (23)⟩`, generated by two independent swaps (order 4);
the dihedral group of order 8, the symmetries of a square, which contains both; and all of `S_4` (order 24).

```scala sc:nocompile
val (s4, generators) = groups.FiniteGroup.permutationGroup(
  4,
  Seq(Seq(1, 0, 2, 3), Seq(0, 1, 3, 2), Seq(2, 3, 0, 1), Seq(1, 2, 3, 0))     // (01), (23), (02)(13) and the 4-cycle (0123)
)
val Seq(swap01, swap23, doubleSwap, _) = generators
val chain = Seq(
  s4.subgroupGeneratedBy(Seq(swap01)),
  s4.subgroupGeneratedBy(Seq(swap01, swap23)),
  s4.subgroupGeneratedBy(Seq(swap01, swap23, doubleSwap)),
  (0 until s4.order).toSet
)
chain.map(_.size)         // List(2, 4, 8, 24)
```

A permutation is its list of images (`Seq(1, 0, 2, 3)` sends 0 to 1, 1 to 0 and fixes 2 and 3), and `permutationGroup` builds the group they
generate and returns the position of each of your generators in it. The filtration value of a simplex of `BG` is the *position in
the chain* of the first subgroup containing every element it uses, so the four subgroups are at times 0, 1, 2, 3:

```scala sc:nocompile
def bars(prime: Int) =
  groups.ClassifyingSpace.persistentGroupHomology(s4, chain, maxDegree = 2, prime = prime).groupBy(identity).view.mapValues(_.size).toMap

bars(2)
// (0, 0.0, Infinity), (1, 0.0, Infinity), (1, 1.0, 2.0), (1, 2.0, 3.0),
// (2, 0.0, Infinity), (2, 1.0, 2.0), (2, 1.0, Infinity), (2, 2.0, 3.0)    each once
```

A bar `(n, i, j)` says: a class of degree `n` first appears in the homology of the `i`-th subgroup and is gone from the `j`-th
(killed, or identified with another class, when you pass to the bigger group); `Infinity` means it is still there in `S_4` itself.
Reading the degree-1 bars:

* `(1, 0, ∞)`: the class from the first subgroup survives all the way to `S_4`. It is the sign of a permutation (the map from
  `S_4` to the group of order 2), which is the one class in `H_1(S_4)`.
* `(1, 1, 2)`: passing to `⟨(01), (23)⟩` brings a new class (the second swap) which dies when we pass to the dihedral group of order 8, in which
  the two swaps are conjugate, hence the same class.
* `(1, 2, 3)`: the dihedral group has a further class of its own, which dies in `S_4`, whose first homology is just the sign.

And in degree 2, there are four bars (`(2, 0, ∞)`, `(2, 1, ∞)`, and two short ones), two surviving to `S_4`: its second homology over the
field with 2 elements has dimension 2, as theory says. Two things to notice. First, **nothing essential is born at the last step**: every
class of `S_4` already lives in the dihedral group of order 8, the subgroup of order 8, a Sylow 2-subgroup. That is a theorem (classes of a group
at a prime come from its Sylow subgroup), and here you can watch it happen. Second, over the field with 3 elements the barcode is just a
point,

```scala sc:nocompile
bars(3)       // (0, 0.0, Infinity) only
```

because every subgroup in the chain is a 2-group and `S_4` has no odd-prime classes in these degrees: the barcode over a prime
`p` sees only what the `p`-part of the group contributes.

## The cost

The size of `BG` is the catch. It has `(|G| - 1)^n` cells in dimension `n`, and computing the homology in degree `k` needs the cells
up to dimension `k + 1`:

| group | `n = 2` | `n = 3` | `n = 4` |
|---|---|---|---|
| S₃ (6 elements) | 25 | 125 | 625 |
| S₄ (24 elements) | 529 | 12,167 | 279,841 |
| S₅ (120 elements) | 14,161 | 1,685,159 | 200,533,921 |

The example above (`S_4`, degrees up to 2, so cells up to dimension 3) is the edge of comfortable. One degree higher for `S_4`
(280 thousand cells) and the second degree for `S_5` (1.7 million) are out of reach for this implementation today, because
the cost grows exponentially with the degree. That is why serious tools (HAP for GAP, for example) compute group cohomology from much smaller
algebraic resolutions rather than from this "bar construction". What this construction has that those do not is the
filtration: it is the natural way to ask the *persistent* question, and the machinery for it already existed.

## The whole script

```scala
import scala.language.experimental.modularity
import org.appliedtopology.tda4j.TDAlab

val lab = TDAlab(2)
import lab.{*, given}

val s3 = groups.FiniteGroup.symmetric(3)
val s3Homology = Seq(2, 3).map(p => p -> groups.ClassifyingSpace.bettiNumbers(s3, 4, p)).toMap

val (s4, generators) = groups.FiniteGroup.permutationGroup(
  4,
  Seq(Seq(1, 0, 2, 3), Seq(0, 1, 3, 2), Seq(2, 3, 0, 1), Seq(1, 2, 3, 0))
)
val Seq(swap01, swap23, doubleSwap, _) = generators
val chain = Seq(
  s4.subgroupGeneratedBy(Seq(swap01)),
  s4.subgroupGeneratedBy(Seq(swap01, swap23)),
  s4.subgroupGeneratedBy(Seq(swap01, swap23, doubleSwap)),
  (0 until s4.order).toSet
)

def bars(prime: Int) =
  groups.ClassifyingSpace.persistentGroupHomology(s4, chain, maxDegree = 2, prime = prime).groupBy(identity).view.mapValues(_.size).toMap

val overF2 = bars(2)
val overF3 = bars(3)
```
