Point-in-time record. Decision document: `DESIGN-package-structure.md` (option C, chosen by the project lead, with two
amendments: `io` flattened into core too, and `groups` merged into the simplicial-set add-on). The resulting rules live
in `CLAUDE.md`; this file is the derivation.

## Flatten (core = algebra, cells, streams, homology, barcode, alpha, io)

Scripted (`flatten.py`, kept in the session scratchpad, not the repo): drop the second `package <pkg>` clause;
delete `import org.appliedtopology.tda4j.<core>.…` in root files, replace it once per scope level by
`import org.appliedtopology.tda4j.{given, *}` in files that stay in a subpackage (`matlab`, `cli`, `tutorial`,
`groups`); keep object-member imports (`…streams.FiniteMetricSpace.MaximumDistanceFiltrationValue`) re-rooted;
`private[<pkg>]` → `private[tda4j]`; FQNs re-rooted in code, scaladoc links and doc fences. Directories are unchanged:
they are now file organization only. `unicode/PrintingHelper.scala` (unused) deleted.

Script misses, fixed by hand:
- `io/CSV.scala` declared `package io` *after* a 20-line package doc comment, beyond the script's 15-line header
  window (the same doc-comment-before-nested-package shape the original reorg tripped on).
- Four `import barcode.*` lines nested inside engine classes (a bare package import, not `tda4j.barcode`-prefixed).
- Partially qualified references `streams.EuclideanMetricSpace(...)` (`AlphaComplexDQP`), `homology.X` in matlab
  specs, `barcode.PositiveInfinity()` in a benchmark spec.
- A cascade worth knowing: a failed `import barcode.*` above `import chainRM.*` produced "type `is` is not declared
  infix" and "`chainRM.List` does not take type parameters" -- not a real shadowing problem, just a failed import
  poisoning the next wildcard. Fix the first error in a file before reading the rest.

### Silent name-binding audit

Spike (scratch Scala 3.9.0 project): in a flat package, a wildcard import (`import lib.*`) silently BEATS a same-named
definition from another file of the same package -- no error, no warning. Under subpackages the same situation was two
wildcard imports of equal rank = a loud ambiguity error. So flattening can turn a compile error into a silent wrong
binding.

Audit method (cheap and complete for this change): temporarily inject `import org.appliedtopology.tda4j.*` at the top
of every root-package file that has a file-level external wildcard import (22 files), compile, and read "ambiguous"
errors -- this puts every library name back at wildcard rank next to `cats.syntax.all.*` etc., so any name that the
flatten made silently-shadowed becomes loud. Result: **0 errors**. Injected lines removed. (Nested external wildcards
are unaffected by the flatten: they out-rank file-level names both before and after.)

## The given-priority problem the project lead hit in a demo

Reported (error text lost): "equal priority givens for Ordering generated by the cell and by the filtration
orderings". Probes with `scala.compiletime.testing.typeCheckErrors` in a package OUTSIDE `tda4j` (to see what a user
sees) against the pre-change library:
- docs-style imports + a user `given Ordering[Simplex[Int]] = stream.filtrationOrdering`: no ambiguity;
- a user given as generic as the library's, or at the same level as the library import: no ambiguity (3.9 prefers
  the more specific/monomorphic candidate);
- `TDAlab` + `cells.{given, *}`: **"Reference to ∆ is ambiguous"** (a name clash, not a given clash);
- `TDAlab` alone: `Ordering[Simplex[Int]]` **not found** (the blanket derivation was not exported).

The flatten itself then reproduced the reported class of bug for real: `SimplicialHomologyEngine()` with no type
arguments inferred **`VertexT = BarcodeEndpoint[Cube]`**. An under-constrained `[VertexT: Ordering]` is solved by
implicit search, and after flattening every top-level generic `Ordering` given of the package was lexically visible
everywhere in it: the blanket `[CellT: OrderedCell] => Ordering[CellT]` (fed by `defaultCubeIsOrderedCell`) and
`[F: Ordering] => Ordering[BarcodeEndpoint[F]]` -- "Ordering from the cell" vs "Ordering from the filtration
endpoints". Likewise `b.upper == PositiveInfinity()` in `CircularCoordinatesSpec` had always been
`PositiveInfinity[Cube]()` (inferred through the same blanket) and only compared equal because case-class equality
ignores the type parameter.

### Fix: no top-level givens; defaults live in companions (implicit scope)

Spike results (scratch project, 3.9.0): a given in a type's companion is found with no import, and is consulted only
when the LEXICAL search finds nothing, so any user/stream given beats it without ambiguity; `A is TC` searches `A`'s
companion; generic code can opt in to a named given by import. Moves:

| was (top-level) | now |
|---|---|
| `given [CellT: OrderedCell] => Ordering[CellT]` | `OrderedCell.cellOrdering`, opt-in by `import OrderedCell.cellOrdering` (only `Homology.scala`, `Cohomology.scala` and one spec needed it) |
| `defaultSimplexIsOrderedCell`, `Show[Simplex]` | `trait SimplexInstances` mixed into `object Simplex`, plus `simplexOrderingFromCell` (`using cell: Simplex[V] is OrderedCell` resolved at the USE site, so a user's filtration-aware cell instance still wins) |
| `defaultCubeIsOrderedCell` | `trait CubeInstances` mixed into `object Cube`, plus `cubeOrderingFromCell` |
| `Show[Chain]` | `Chain.chainShow` |
| `[F: Field] => Show[F]` | opt-in `Field.showFromField`; `Fp` gets `Fp.showFp` in its own companion |
| `Ordering[BarcodeEndpoint[F]]` | `BarcodeEndpoint.endpointOrdering` (new companion) |
| `[F: Filterable] => Option[Filterable[F]]` | deleted: duplicate of `Filterable.optionalFilterable` |

Rule: **the core package has no top-level givens.** Consequence for users: `import org.appliedtopology.tda4j.*`
suffices (no `given` selector needed).

## TDAlab

Project lead, mid-session: drop the namespace objects (`tdalab.streams.X` etc. existed only to ease moving between
subpackage imports and lab code), but keep re-exports so `import tdalab.{*, given}` remains the only import a lab user
needs. Spike (3.9.0): when a user imports BOTH the package and `tdalab.*`, re-exported objects, classes, companions and
types are NOT ambiguous; re-exported defs ARE ("Reference to bar is ambiguous") and re-exported extension methods
silently stop resolving. Hence:
- `∆` became `object ∆` (`apply` + `unapplySeq`), so it re-exports safely and pattern-matches;
- TDAlab re-exports every public top-level class/trait/object/type/enum of the root package and of the add-on (minus
  `TDAlab` itself and the companion mixins), generated by `.claude/scripts/tdalab-exports.py` between
  `BEGIN/END generated re-exports` markers; never defs/extensions (`asSimplex`, `asCube`, `simplexOrdering`, ...);
- no given re-exports at all (defaults come from companions now), so the old "deliberate re-export" lines are gone.
