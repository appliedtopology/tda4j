\section{How correctness is established}\label{sec:correctness}

A persistent homology library can be wrong in ways that no unit test on Betti numbers will show: a pairing with the right
count and the wrong bars, a filtration whose ties disagree with its engine, a field in which every sign error cancels. The
library is developed under a methodology designed around that fact. We describe it because the benchmark in
\cref{sec:evaluation} is only as meaningful as the agreement checks behind it, and because we think the incidents,
which are the empirical content of this section, are of use to the authors of other libraries.

\subsection{Oracles that the plausible wrong answer fails}\label{sec:oracles}

A specification is \emph{discriminating} if the plausible wrong implementation fails it.
\begin{itemize}[leftmargin=1.5em, itemsep=2pt]
\item \textbf{$\Fsev$ or $\mathbb{F}_3$ against $\Ftwo$} for signs: over $\Ftwo$ a sign error is invisible, so every engine is tested
  at an odd prime, and signed-field fixtures need at least five vertices, since a hash-ordered set of four or fewer elements
  hides an ordering bug.
\item \textbf{Cup products against Betti numbers} for simplicial sets: they distinguish spaces with the same Betti numbers, and they
  caught a wrong torus fixture that the Betti numbers accepted.
\item \textbf{Cell for cell, value for value} against an independent construction for every stream, with tie-heavy inputs;
  a new complex is compared with the hand-wrapped construction class, because Betti numbers do not catch a wrong $+1$.
\item \textbf{Reference engines kept in the test tree}: each fast engine has a slower reference that it must equal bar for bar
  and term for term (the packed Ripser engine against a \code{Chain}-based one; the dense cohomology engine against the
  cell-keyed one; the signed union-find against the first, eager implementation; the collapsed nerve against the bar construction).
  \emph{Two engines agreeing is no proof if they share a code path}: hand-derived fixtures are the real oracle.
\item \textbf{Mutation checks} on new code: a check that cannot fail is worthless, and some can fail on rare inputs only: a missing
  pivot check showed on five of three hundred tie grids. A uniform sign flip of every coboundary changes no output, so
  sign mutations must be non-uniform.
\item \textbf{Pivot checks at run time}: the involution checks every pivot against the pairing and throws on a mismatch
  (\cref{sec:representatives}); a reduction that moves backwards or stands still for 64 steps throws too.
\end{itemize}

\subsection{The documentation is a test}\label{sec:docs-tests}

The tutorials state numbers (the number of bars of a torus, the bars of a Truchet tiling), and a specification asserts each
of them; the code fences of the documentation are compiled by its build. Documentation that is wrong breaks the build, and the
first five lines a newcomer writes are the ones we test first.

\subsection{A cross-library agreement check}\label{sec:agreement}

The benchmark harness (\cref{sec:protocol}) does not only time tools: it compares each tool's barcode with a reference's before
it reports a time, degree by degree, by bottleneck distance. The tolerance follows from the inputs, since ripser.cpp computes
in single precision, JavaPlex quantises filtration values, and an asymmetric matrix has no single barcode. Every tool is given
the same canonicalised input; zero-length and essential bars follow one stated convention; and an alpha radius and a squared
radius are converted explicitly (GUDHI's alpha filtration values are squared radii). A row that does not agree is a finding,
and the tables report it with the cause, ours or theirs. The reference is the one the harness assigns per task (ripser.cpp for
Vietoris--Rips and for sparse filtrations, GUDHI elsewhere); a case flagged as degenerate (a cospherical input, on which every
Delaunay-based tool triangulates the degenerate cells its own way) has no ground truth and is paired with a jittered copy in
general position.

\subsection{Defects found in references}\label{sec:references}

Building features against published algorithms and reference code turned up three defects, each verified rather than
suspected; we report what was verified and nothing more.
\begin{itemize}[leftmargin=1.5em, itemsep=2pt]
\item \textbf{Cavanna--Jahanseir--Sheehy~\cite{cavanna2015sparse}, Algorithm~3.} The algorithm computes an edge's birth time from its
  two endpoints only, with no check against the radius past which a point's ball is empty; the paper's own Section~5.3,
  which gives the general rule, requires one. A hand-verified counterexample ($\varepsilon=1$, $\lambda_i=1$, $\lambda_j=10$,
  $d=10$) has Algorithm~3 return $8$ although $p_i$ vanishes at $4$, so over the interval $(4,8)$ the edge would be present
  while its endpoint's ball is already empty.
\item \textbf{DREiMac's \code{\_gram\_schmidt}}~\cite{scoccola2022toroidal}. The subroutine projects each new vector onto the original
  basis vectors instead of the orthogonalised ones; on $(1,0,0),(1,1,0),(1,1,1)$ it returns a third vector that is not orthogonal
  to the first. The bug is invisible with two classes, the headline torus case. We did \emph{not} find an end-to-end failure: on
  300 random $3\times3$ integer bases the final output was always LLL-reduced. This is a defect in an isolated subroutine, not a
  demonstrated error in toroidal coordinates.
\item \textbf{The PH-roadmap's \code{fractal\_9\_5\_2} distance matrix} (\cref{tab:pitfalls}) is not symmetric; tools that read different
  triangles compute from different inputs. Whether any tool other than ours misbehaves on it has not been checked.
\end{itemize}
\VERIFY{none of the three has been reported upstream; decide whether to file reports before submission}
